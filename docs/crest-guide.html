Research pipeline

CREST runs three research systems on the same questions, saves their answers, and compares creative quality with two AI judges.

Read the completed 50-question comparison →
PipelineQuick startSystemsParallelismResults and reuseRanking method

Three stages, one result directory

  1. 01

    Generate answers

    Caesar, OpenAI (Sol + web search), and Google Deep Research answer each question independently.

    50 questions → 150 saved answers
  2. 02

    Compare each pair

    Two judges choose one overall A/B winner, guided by New, Useful and Surprising. Every pair appears in both orders.

    150 answers → 600 judgments
  3. 03

    Analyze preferences

    Count wins, rank the systems, and report uncertainty, judge agreement and order effects.

    600 judgments → ranking and diagnostics

The bundled dataset preserves Caesar’s 50 question texts and adds their five paper categories, with 10 questions per category. These counts describe a complete run; a one-question pilot produces 3 answers and 12 judgments.

Start with one question

Run these commands from the repository root. Generation and judging make paid API calls; planning and analysis run locally.

Install and set credentials

Use Python 3.11–3.13. Caesar also needs the sibling ../rome checkout and its dependencies.

python -m pip install -e '.[test]'
python -m pip install -e ../rome
export OPENAI_API_KEY=...
export GOOGLE_API_KEY=...

GEMINI_API_KEY also works. Credentials come from the environment. To use an existing Rome environment, set research.caesar.python_executable in your configuration.

1. Plan and generate

Preview missing calls, then create the pilot run.

python -m crest plan --limit 1
python -m crest generate --limit 1

Copy the printed run_dir into CREST_RUN below. Omit --limit 1 to generate all 50 questions.

2. Judge and analyze

Replace the placeholder with your result directory.

CREST_RUN=crest/results/YYYY-MM-DD/HH-MM-SS-TZ-ID
python -m crest judge --run "$CREST_RUN"
python -m crest analyze --run "$CREST_RUN"

For all three stages together, use python -m crest run. Add --dry-run to preview work without API calls.

Commands use crest/configs/crest.yaml. Add --config crest/configs/crest.mbp.yaml for the 64 GB jason-mbp profile. Use the same configuration for each stage.

Resume generation or rerun judging 
python -m crest generate --run "$CREST_RUN"
python -m crest judge --run "$CREST_RUN"
python -m crest analyze --run "$CREST_RUN"

Completed matching work is reused. To change judges or rubric, edit your configuration and rerun stages 2 and 3 with this directory. Stage 1’s saved answers stay available. Later stages otherwise select the latest generation run; an explicit --run avoids ambiguity.

Parallelism, retries and budget

Providers run concurrently. A provider gains one slot after two successful uncached jobs and halves its limit after HTTP 429, with a shared cooldown.

WorkDefault: start → maximumjason-mbp: start → maximum
Caesar answers1 → 420 → 20
OpenAI answers3 → 122 → 6
Google answers2 → 81 → 4
Research total6 → 2423 → 30
Both judges combined8 → 3216 → 32

Limits apply to one pipeline process. Other account traffic can still trigger rate limits. Each judge can reach 16 concurrent requests.

$5 per answer is a target. Caesar reserves estimated request costs and writing time; its configured worker timeout is two hours. Neither setting guarantees a complete answer or a final invoice below $5. Hosted research APIs expose no hard dollar cap, and judging costs extra.

What happens after a failed request?

Retries are bounded, with backoff and provider cooldowns. Native job creation is retried only after an explicit rate-limit rejection; uncertain submissions require reconciliation. Existing remote job IDs are retrieved after interruption. Invalid judge responses can receive up to four attempts, with failed attempts retained in cost records.

  • One run, separate stages. Each executed stage creates a dated directory inside its run. Analysis reads a precise judgment snapshot.
  • Local directory names. results_timezone: America/Chicago uses local dates and CDT/CST. Recorded event timestamps stay in UTC.
  • Answers carry their settings. Configuration IDs link each answer to frozen models, settings and source provenance. JSONL files are canonical; Markdown files are reading copies.
  • Costs and times stay with the work. Records retain usage, cost estimates, unknown charges and elapsed time. Cache hits preserve the original timing.
Which changes reuse the cache?
  • Changing judges or rubric reuses saved answers and regenerates only judgments that no longer match.
  • Changing research settings needs a new generation run; unaffected answers can come from the shared cache.
  • Changing concurrency or retry settings preserves paid cache identities.
  • For intentional fresh calls, increment the provider’s revision. Resolve uncertain submissions before doing so.

How the ranking works

  • NewWhat is original about the central contribution?
  • UsefulHow well does it serve this question and support its payoff?
  • SurprisingHow meaningfully does its approach depart from the expected one?

These qualities guide one overall A/B choice, with a comparative explanation. They are not separate scores or votes. Every pair receives two judges in both answer orders, giving 12 judgments per question.

Win rate = wins ÷ comparisons
A complete run gives each system 400 comparisons: 50 questions × 2 opponents × 2 judges × 2 orders.

Questions, opponents, judges and orders receive equal weight. If the judge cannot support a substantive preference, the rubric instructs it to choose A; consistent indifference in both orders splits the votes evenly.

Reported 95% intervals resample whole questions 1,000 times, keeping each question’s comparisons together. They describe sensitivity to the question mix while holding the saved answers and judges fixed. These are observed AI preferences, with no human validation or independent fact-checking.

Choose the rubric file

The default nus_pairwise_v2.txt emphasizes substantive contributions, task-relative usefulness and meaningful surprise. It treats unfamiliarity as uncertainty about novelty. The v1 wording is also available. Select either file with the configuration’s rubric field:

# In a configuration under crest/configs/:
rubric: ../prompts/nus_pairwise_v2.txt
# Or use the original wording:
# rubric: ../prompts/nus_pairwise_v1.txt

Either file uses the same presentation and validation: URL destinations are hidden uniformly, meaningful citation labels remain, and explanations are screened before acceptance. Original answers and the exact judging prompt remain saved.

Method and references

The complete design, exclusions and diagnostics are in Research evaluation. Creativity guidance draws on Runco and Jaeger (2012); pairwise win ranking has a basis in Shah and Wainwright (2018). Dror et al. (2018) discuss resampling in evaluation, and Zheng et al. (2023) examine LLM judge biases. These references do not validate this rubric as a general creativity test.

The five question categories follow the Caesar paper, Appendix B.1. The completed report includes all 150 answers and 600 judgment explanations.
