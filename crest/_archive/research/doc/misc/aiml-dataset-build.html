AI/ML CREST dataset — build report

⚠ THIS REPORT DESCRIBES A SUPERSEDED BUILD (annotated 2026-07-31)

It documents the 41-item intermediate state. The shipped file question/crest_aiml_challenges.jsonl now has 50 items, 10 per category: ids 00–40 are unchanged and every per-item finding below still points at a real item, but ids 41–49 are new (C4 ×3, C5 ×6) and are covered by NOTHING in this report — no audit record, no discrimination review, no dedupe check.

Three items this report marks BLOCKING are CLOSED:

  • §8.1 the 9 missing items — authored and appended as _41–_49.
  • §7 schema incompatibility — question/schema.json is now crest-challenge/3.2.0 with the twelve-value domain enum, and all 50 items load and validate.
  • §8.2's provenance loss — the C5 source is tracked at question/aiml_build/c5_source_verbatim.json. The unaudited half of §8.2 still stands.

§5's distributions are re-measured in place below. §0, §4 and §7 are superseded and cut to their surviving conclusions. This dataset is not wired into config/eval_config.yaml, has no item_design.jsonl rows (so ci_check.sh's bijection check does not cover it), and has never been run or scored. It is not the dataset any published CREST number refers to.

Built 2026-07-31. Output: question/crest_aiml_challenges.jsonl (one JSON object per line, UTF-8, LF-terminated).

0. HEADLINE — the build shipped 41 of 50; the remaining 9 were authored later. CLOSED.

At build time the five category batches were not all available: C1/C2/C3 had 10 each on disk, C4 had 7 (questions/c4_ml_new10.audited.json, committed mid-audit), and C5 had no source file at all — 5 items were transcribed verbatim from the task prompt, and the prompt itself cut off inside item 6. Nothing was invented to reach 50 at the time, which was the right call: the alternative was authoring 8 items with fabricated prior-art catalogues.

The 9 were authored separately and appended as ids _41–_49, so the file is 50/50 and squared at 10 per category. They were NOT produced by this build and carry none of its audit apparatus — see the header. The C5 transcription is now tracked at question/aiml_build/c5_source_verbatim.json; it remains unverified against any original (§8.2).

2. Fabrication and date errors caught, and how each was resolved

Zero outright fabrications were found in any batch. Every named paper, DOI, arXiv id, statute and system in the shipped file resolves to a real artifact. The defect class that actually dominated is concept-date inflation: prior art dated to a later paper, product launch, rebranding or venue rather than to first publication. In every case found, the error ran in the direction that makes the prior art look younger — i.e. that makes a submission look more novel than it is, which directly inflates the New score. Not one error ran the other way.

3. Items dropped

One item dropped, for cross-category duplication.

C5_alignment_safety_03 — DROPPED (dedupe against C4_alignment_safety_32)

Both items pose the same open problem: detect reward hacking while an RL run is still going, without a trustworthy gold signal, and report the overhead, the trigger threshold, the false-alarm handling and the blind spots. A single well-constructed answer satisfies both asks. Lexical Jaccard on the two queries is only 0.103 — the collision is semantic, and was caught by reading, not by the overlap scan.

C4_alignment_safety_32 was kept and C5_alignment_safety_03 dropped, for three reasons:

  1. Stronger discrimination. C4 requires three distinct outputs (R1 genuine improvement; R2 proxy rising via a stylistic correlate; R3 true quality rising while the proxy stays flat because the reward model underrates it). R3 in particular is a discriminator that almost no naive answer produces. C5's only discrimination requirement is "name a class of hack it cannot catch."
  2. Validation protocol. C4 rule (b) demands a positive control with reward hacking deliberately induced, plus a reported detection rate and false-positive rate. C5 has no validation requirement.
  3. C5's exclusion list leaks. C5 bans reward-model ensembles, adversarial verifiers, CoT-reading monitors, KL/entropy penalties and post-hoc transcript review — but its own expert_baseline names the convergent answer as "a trusted held-out probe set scored periodically during the run", which none of its own hard rules exclude. The item therefore fails to box the expert baseline out, which is the entire point of a C5 item. That is an independent defect, not just a tie-breaker.

Cost: C5 falls from 5 items to 4.

Not dropped, but adjacent — flagged for human adjudication

Five further pairs sit close enough that a reviewer should confirm the call. In each case the deliverable differs even though the topic overlaps, which is the test applied here (would one answer substantially answer the other?).

Pair Shared topic Why kept
C1_evaluation_benchmarking_04 / C4_evaluation_benchmarking_34 black-box contamination C1 wants a hypothesis test (statistic, null distribution, provable FPR ≤ 5%, power); C4 wants an effect-size estimate (how many score points of inflation, with uncertainty). No items were dropped for schema failure. All 42 candidates passed every content check.

4. Schema enforcement

The build-time checker (.tmp_build/assemble.py) passed 0 errors on the 41 items it wrote. This section is superseded by the live gate: all 50 items now validate against question/schema.json (crest-challenge/3.2.0) via harness/run_crest.load_challenges, which is the check that matters. The one build-time convention worth keeping on the record:

  • Every item's known_answers carries ≥ 8 substantive entries with both a resolvable identifier (arXiv id / DOI / stable URL) and a 4-digit year, on top of a leading Dated as of … preamble entry that carries neither by design and is excluded from that count. (This is a markedly stricter dating bar than the shipped CREST set achieved — datasheet.md §2.)

Two known_answers entries do not match the identifier/year regex and were manually cleared as false positives, not defects:

  • C2_systems_efficiency_17 — the BIS advanced-computing control entry. Its identifier is the ECCN (3A090) and the Total Processing Performance metric, not an arXiv id or DOI. Valid.
  • C3_systems_efficiency_27 — the MQA/GQA/MLA cache-reduction entry. Carries three arXiv ids (1911.02150, 2305.13245, 2405.04434) but no spelled-out year; the years are encoded in the arXiv ids. Valid, though spelling out "2019 / 2023 / 2024" would be more consistent with the rest of the file.

6. Discrimination evidence, per item

"Discrimination" = the machinery in each item that separates a strong answer from the convergent expert baseline. Each category uses a different device, and the strength is uneven.

C1 (n=10) — program-checkable arithmetic + numeric prior-art delta

Every C1 item carries R-CLOSEST PRIOR ART: name exactly ONE published method and give a numeric delta on the item's binding metric; "ours differs" with no number FAILS; a zero delta honestly reported is allowed. That last clause is the real discriminator — it removes the incentive to bluff. Plus item-specific arithmetic gates:

item binding numeric gate
C1_architectures_training_00 per-layer byte table summing to ≤ 2.56e8 bytes at L=1e6; R5 forces a bits-required-vs-bits-budgeted accounting, and the design FAILS on its own arithmetic if R5 > R1
C1_architectures_training_01 R3 forces computing the random-routing reference (2048 ± Poisson, r≈1.07) rather than asserting balance; R6 forces converting expert-level ratio r to device-level r_dev over 32 devices and using r_dev for any throughput claim
C1_alignment_safety_02 FLOP breakdown ≤ 1.3× vanilla PPO; R5 forces an eval-set size computation with clustered SEs such that the CI half-width is < 2%
C1_alignment_safety_03 expected audits ≤ 100 over 10,000 tasks, arithmetic shown, including audits triggered by resampling/escalation
C1_evaluation_benchmarking_04 R6 separates permutation replicates (free) from fresh model generations (costly) inside a 20,000-generation budget
C1_evaluation_benchmarking_05 R4 requires using the 1,000 per-item scores and per-checkpoint loss — a criterion from the 12 aggregate accuracies alone FAILS; R5 forces seed variance into the noise model
C1_systems_efficiency_06 R6 requires 128k degradation reported separately from short-context, because cache-quantisation error accumulates with sequence length and weight-quantisation error does not

C2 (n=10) — scope locks + explicit no-credit list

C2's device is negative: 66 KNOWN AND BINDING tags naming facts the answer may not contradict, plus 2 KNOWN AND EXPLICITLY EXCLUDED FROM CREDIT tags naming the obvious answer so it earns nothing. Examples that bite hard:

  • C2_architectures_training_10: prefill/decode accounting rule — "long inputs become free" is invalid; and the low-bit-serving rule that must be reconciled with Quamba's outlier evidence.
  • C2_architectures_training_11: "this world has no reversal curse" is explicitly excluded from credit (it is arXiv:2406.05183), and so is "they would invent a block-wise cache" (arXiv:2503.09573, arXiv:2505.22618).
  • C2_alignment_safety_12: must name a respect in which the world is less safe, and must distinguish exploiting reward-model error from tampering with the reward channel.
  • C2_evaluation_benchmarking_15: must separate predictability of capability from predictability of propensity.
  • C2_multimodal_agents_19: must not conflate semantic transfer with transfer of computational structure (arXiv:2103.05247).

Weakness: 4 of 10 C2 items (_11, _13, _14, _17) have no explicit discrimination clause in hard_rules — they rely entirely on the known_answers no-credit list. That is weaker than an in-rule gate, because a judge reading only the rules will not see it.

7. COMPATIBILITY — CLOSED 2026-07-31

At build time question/schema.json pinned domain to the six ORIGINAL domains, so all 41 items failed validation on domain and nothing else — every other constraint (id pattern, required, additionalProperties: false, the two other enums, minLength, minItems) already passed. The schema has since been bumped to crest-challenge/3.2.0 with a twelve-value domain enum, and all 50 items load and validate through harness/run_crest.load_challenges.

The trade-off that decision made, and which is now live: a union enum permits an arts/humanities item to be tagged systems_efficiency. The alternative considered was a second schema file selected per dataset, which would need a change to load_challenges' _SCHEMA constant. That was not done.

Two compatibility notes that are still open:

  • ci_check.sh enforces an id bijection between question/crest_challenges.jsonl and question/item_design.jsonl. item_design.jsonl has no rows for these 50 ids, so this dataset has no design-rationale sidecar and the bijection gate does not cover it.
  • expert_baseline is judge-hidden as of 2026-07-30 and is not read by judge/score.py::_judge_prompt. It is carried here for provenance only. Nothing in §6's discrimination analysis reaches the judge unless it is also in hard_rules or known_answers — which is precisely why the four C2 items and two C5 items with no in-rule discrimination clause are flagged (§8.4).

8.5 Confounded design axes

axis_isolated is near-1:1 with category (C3/C5 share novelty; C4 and C5 each carry one off-label item — §5). time_sensitivity is near-confounded: C2 and C4 are 100% pre_cutoff, so every post_cutoff item is C1, C3 or C5. Any model comparison crossing category with time sensitivity will not identify. Decide whether that is intended before running.

8.6 Post-cutoff citations to future-dated arXiv ids

The catalogues cite ids in the 2602–2606 range (e.g. arXiv:2603.28063, 2604.16242, 2606.04923, 2605.26047, 2604.09780, 2606.09711). These are load-bearing — several are named as the closest prior art and therefore set the novelty bar. They should be re-resolved immediately before release; if any fails to resolve, the novelty gate on that item is void. C3_alignment_safety_22's gate rests entirely on arXiv:2603.28063 resolving.

8.7 Two style inconsistencies in known_answers

C3_systems_efficiency_27's MQA/GQA/MLA entry carries arXiv ids but no spelled-out year, and C2_systems_efficiency_17's BIS entry uses an ECCN rather than a DOI. Both are valid; both differ from the file's convention. Normalise or leave.
