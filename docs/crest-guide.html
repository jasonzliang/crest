Research pipeline

CREST runs four research systems on the same questions, then uses three AI judges to compare the saved answers. This guide covers setup, execution, saved results and ranking.

Read the latest completed comparison, v2

The latest study uses three research systems and two judges. The previous comparison, v1 is preserved with its original questions and settings.

PipelineQuick startSystemsParallelismResults and reuseRanking method

Three stages, one result directory

  1. 01

    Generate answers

    Caesar, OpenAI (Sol + web search), Google Deep Research, and Anthropic (Sonnet + web search) answer each question independently.

    50 questions → 200 saved answers
  2. 02

    Compare each pair

    Three judges choose one overall A/B winner using the selected rubric. Every pair appears in both orders.

    200 answers → 1,800 judgments
  3. 03

    Analyze preferences

    Count wins, rank the systems, and report uncertainty, judge agreement and order effects.

    1,800 judgments → ranking and diagnostics

The bundled dataset has 50 questions generated by the three judge models, 10 per category, in the five categories of Caesar’s original set, which the published comparison used; each row records the generating model. These counts assume all work succeeds; a complete one-question pilot has 4 answers and 36 judgments.

Start with one question

Run these commands from the repository root. Generation and judging make paid API calls; planning and analysis run locally.

Install and set credentials

Use Python 3.11–3.13. Clone Caesar alongside CREST as ../rome, then install both projects in a virtual environment:

git clone https://github.com/jasonzliang/caesar-agent.git ../rome
python -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[test]'
python -m pip install -e ../rome
export OPENAI_API_KEY=...
export GOOGLE_API_KEY=...
export ANTHROPIC_API_KEY=...

If ../rome already exists, use that checkout. GEMINI_API_KEY also works. Credentials come from the environment; CREST does not load dotenv files. To use an existing Rome environment, set research.caesar.python_executable in your configuration.

1. Plan and generate

Preview missing calls, then create the pilot run.

python -m crest plan --limit 1
python -m crest generate --limit 1

Copy the printed run_dir into CREST_RUN below. Omit --limit 1 to generate all 50 questions.

2. Judge and analyze

Replace the placeholder with your result directory.

CREST_RUN=crest/results/YYYY-MM-DD/HH-MM-SS-TZ-ID
python -m crest judge --run "$CREST_RUN"
python -m crest analyze --run "$CREST_RUN"

For all three stages of the one-question pilot, use python -m crest run --limit 1. Add --dry-run to preview work without API calls; omit --limit 1 for all 50 questions.

Commands use crest/configs/crest.yaml, the single master configuration that holds every model, prompt, budget, depth and concurrency setting. Concurrency values for the 64 GB jason-mbp machine are kept as comments beside the Caesar, OpenAI, Google and judge defaults. Configuration paths are relative to the YAML file. Keep the same configuration across stages unless intentionally changing the judges, rubric or analysis settings. --agents and --judges accept any subset of the configured names.

Resume generation or rerun judging 
python -m crest generate --run "$CREST_RUN"
python -m crest judge --run "$CREST_RUN"
python -m crest analyze --run "$CREST_RUN"

Completed matching work is reused. An existing run keeps its original questions, systems and generation settings. To change judges or rubric, edit the configuration and rerun stages 2 and 3 with the same --run. Without --run, judging and analysis select the latest generation run.

Parallelism, retries and budget

Providers run concurrently. A provider gains one slot after two successful uncached jobs and halves its limit after HTTP 429, with a shared cooldown.

Totals sum the separate provider limits; they are not a shared pool. Limits apply to one pipeline process, and other account traffic can still trigger rate limits. Each judge starts at 4 and can reach 16 concurrent requests. Values for the 64 GB jason-mbp machine are comments in the master configuration.

Every research agent has a $4 per-answer warning threshold (budget_usd: 4.0). Research settings aim at about $3; Google's 600-word pilot fell below the $2–4 range. Every agent currently runs with budget_cap: soft: an overrun is flagged in the answer’s warnings and in the report, and nothing is stopped. With hard the budget is enforced (Caesar’s SDK audit refuses calls beyond it, OpenAI cancels the hosted job once observed usage passes it, Anthropic starts no further server turn); auto enforces it and overrides the depth settings with values crest/budget.py derives from it; every override is printed when the config loads and listed by crest plan. Google can only be soft because the managed agent exposes no depth control. Caesar’s derived worker timeout is 3.5 hours for the whole answer. OpenAI and Anthropic also have a budget_floor_usd of 3.0: when a finished answer cost less, the shared research_continuation_prompt is sent as the next turn of the same conversation and the agent researches further and rewrites the answer, up to max_research_rounds rounds (6 for OpenAI, 14 for Anthropic), aiming at about $3 inside the $2–4 range; a round starts only if it would not overshoot that aim by more than the current shortfall, and under a hard or auto cap only if it also fits under budget_usd. None of these settings guarantees a complete answer or a final invoice below the target. The published 2026-10-26 run measured $1.60 (Caesar), $0.10 (OpenAI) and $3.71 (Google) per answer; the research settings have since been raised, so run a one-question pilot to measure spending before a full run. What happens after a failed request?

Retries use backoff and shared provider cooldowns. Hosted job creation is retried only after an explicit rate-limit rejection; uncertain submissions require reconciliation. After interruption, CREST retrieves saved remote job IDs. Rejected judge responses allow up to four attempts by default, and the cost records retain failed attempts.

Which changes reuse the cache?
  • Changing judges or rubric reuses saved answers and regenerates only judgments that no longer match.
  • Changing research settings needs a new generation run; unaffected answers can come from the shared cache.
  • Changing concurrency or retry settings preserves paid cache identities.
  • For intentional fresh calls, increment the provider’s revision. Resolve uncertain submissions before doing so.

How the ranking works

The default NUS rubric uses New, Useful and Surprising; the optional AUT-inspired rubric uses Fluency, Flexibility and Originality. Either guides one overall A/B choice with a comparative explanation. Criteria do not receive separate scores or votes.

Compare every pair in both orders

For each question, each judge sees all six system pairs twice, with A and B swapped: 6 pairs × 3 judges × 2 orders = 36 judgments. Provider labels and URL destinations are hidden; meaningful citation labels remain. Judges receive the complete answer text without tools, though wording may reveal the authoring system.

If the judge cannot support a substantive preference, it must explain that indifference and choose A. Consistent indifference in both orders splits the votes evenly. Identical presented answers are skipped without inventing a winner.

Rank only complete questions

A question contributes only when every system has exactly one completed, nonempty answer and every pair, judge and order has exactly one valid judgment. A missing answer, missing judgment, duplicate completed answer or duplicate valid judgment excludes the whole question from the pooled ranking and each judge’s ranking. Invalid judgments provide no votes.

Win rate = wins ÷ comparisons
A complete run gives each system 900 comparisons: 50 questions × 3 opponents × 3 judges × 2 orders.

Questions, opponents, judges and answer orders receive equal weight. The highest win rate ranks first; equal rates share a rank. Head-to-head tables show preferences for each system pair, while per-judge results use the same complete questions as the pooled result.

Read uncertainty and diagnostics together

By default, 95% percentile intervals use 1,000 bootstrap samples of whole questions, drawn with replacement using seed 2026. Each sample keeps a question’s judgments together. The analysis reports intervals for win rates, ranks and differences between systems’ win rates. A pair’s ordering stability is the fraction of samples where either system ranks higher or they tie; it is not a probability that one system is truly better.

These intervals describe sensitivity to the observed mix of complete, curated questions. They hold the saved answers, selected judges, rubric and observed judgments fixed. They omit variation from generating new answers, choosing other judges or assessing whether the rubric measures creativity well.

Diagnostics report A-position preference, changes in winner after swapping answer order, judge disagreement and preference cycles. A swap change combines order effects and sampling variability; one judgment per presentation cannot separate them. These are AI preferences, without human or domain-expert validation or independent fact-checking.

Choose the rubric file

Set the configuration’s rubric field to the desired prompt. The default is nus_pairwise_v2.txt; the archived NUS v1 wording is preserved unchanged for reproducibility. The AUT-inspired prompt remains an alternative:

# In a configuration under crest/configs/:
rubric: ../prompts/nus_pairwise_v2.txt
# Historical comparisons only: original NUS wording
# rubric: ../_archive/reference/nus_pairwise_v1.txt
# Alternative: AUT-inspired comparison
# rubric: ../prompts/aut_pairwise_v1.txt

The old AIS v1 path remains a compatibility link to the archive. V2 credits substantive combinations rather than the least recognizable component, treats missing prior-art knowledge as uncertainty, and evaluates usefulness within the task’s premises. These are design improvements, not measured gains in agreement with human judges. Neither rubric was changed during archival.

All use the same answer presentation and response checks. Checks reject obvious noncomparisons and unfinished explanations; they do not verify factual accuracy or whether the explanation supports the winner. Original answers and exact prompts remain saved. Rerun judging and analysis after changing the rubric; different rubric families cannot share one ranking.

Method and references

Shah and Wainwright (2018) study ranking by pairwise wins. Dror et al. (2018) discuss statistical testing and resampling in evaluation, and Zheng et al. (2023) examine LLM judge biases. These sources inform the design; they do not establish the rubric’s validity or guarantee the reported intervals apply to other tasks.

The five question categories follow the Caesar paper, Appendix B.1. The latest completed report includes all 150 answers and 600 judgment explanations. The previous report remains available separately.
