Historical document. Preserved for context; use the research pipeline guide for current experiments.

Archive storage. This note was moved from crest/_archive/research/result/. Result data remain there locally and are excluded from Git. Any tracking instructions below describe the earlier layout.

Each evaluation writes a run directory. Runs are immutable: every invocation mints a new run_id and nothing is ever resumed into an existing one. There is no --resume / --no-resume. What stops you re-paying is the cross-run generation cache (harness/cache.py, on by default): an agent answer already stored in any previous run is served for free, keyed by (challenge text, agent, model, adapter fingerprint), so a re-run costs judge calls only. Disable it with --override-cache (all entrants) or --override-cache-agents <keys> (just the named ones), or use_cache: false in the config. To repair judge failures in place without minting a new run, use python -m crest.harness.rejudge --run <run_dir>.

run_id = <UTC-timestamp>__crest__<subset>__git<sha>__<nonce> — sortable and provenance-encoding. Run outputs are ~7 MB per run, so runs/, index.jsonl and latest are gitignored and live on disk only; they are both the generation cache and the evidence base, so do not delete them.

  • "the numbers in the paper" → leaderboard.json. It carries the primary endpoint min(New,Useful,Surprising) per agent (which summary.json does NOT), the run's provenance including derived warnings about it, and the caveats -- chiefly that judge severity exceeds the between-agent spread, so the ordering is not identifiable from this run.
  • "the latest run" → latest.
  • "what runs exist" → index.jsonl.
  • Analyze a run: python -m crest.analysis.stats --run crest/result/runs/<run_id>/records.jsonl.
  • Is a long run still alive? python -m crest.analysis.stall_check.

RECORD_SCHEMA_VERSION in harness/results.py is now crest-record/1.2.0; the shipped run 040653Z was written under the previous version and all 250 of its records — and its manifest — stamp crest-record/1.0.0. scoring_status is one of scored · judge_degraded (scored, but by fewer than min_judges — excluded from headline numbers) · empty_answer (the adapter returned no text; an ADAPTER failure, deliberately distinguished from fabrication) · too_short (non-empty but under the substantive-length floor -- same adapter root cause as empty_answer, but kept separate because the threshold is a judgement call) · grounding_fail · judge_error (no judge survived). creativity is null on every UNSCORED path — never a fake 0 — but judge_degraded is the exception: it carries a full creativity dict scored by too few judges, which is why results.py::is_scored requires BOTH scoring_status == "scored" and a non-empty dict (three disagreeing definitions of "scored" once made a repair drop the headline count from 100 to 91). Records written by run_crest carry query_sha + adapter_fp (the cache's content address); the shipped run 040653Z predates adapter_fp, truncated, answer_chars and answer_words — 0 of its 250 records have them, so the cache indexes none of it and answer-length covariates cannot be computed from that release. Records also carry generation_cached / cache_source_run, so a reused answer is visible in the data.

Per-judge scores are a list under creativity.judges, each row stamped with same_family, so pandas.json_normalize(record_path=["creativity","judges"], meta=[...]) yields a rater-level frame for the mixed-effects model (750 rows on run 040653Z). The leave-one-family-out subset is the rows with same_family == False — LOFO drops the same-family judge, so keeping == True selects the exact complement (500 vs 250 rows on that run). creativity.judge_protocol records which protocol produced the row (full-panel (same-family as covariate) by default).

Reliability (Krippendorff α / ICC) and inferential stats live in crest/analysis/stats.py, not in summary.json.

make_manifest derives judge_protocol from panel.protocol, so it agrees with the per-record creativity.judge_protocol. Run 040653Z's manifest was written before that fix and hand-corrected; its judge_protocol_note records exactly that.
