Paper comparison method

This pipeline compares released papers from ScientistOne, ScientistTwo, Sakana AI Scientist (v1), Sakana AI Scientist (v2), and Sakana Agentic Scientist (v3). It samples paper pairs, collects overall creativity preferences, and gives each opponent equal weight.

The target is the released collection. Results describe the papers the judges preferred, rather than performance on identical tasks or a prediction of future work. Topics, publication dates, underlying models, computing resources, and release choices differ across collections.

Comparison design

  1. Freeze eligible paper lists and hashes. Keep outputs explicitly labeled as human–AI co-discovery outside the primary pool.
  2. For each of ten scientist matchups, sample up to ten distinct paper pairs uniformly without replacement. Use every pair if fewer than ten exist. Each paper has the same selection probability as other papers in its collection.
  3. Use two judges and both A/B orders: four judgments per pair. Each response contains one comparative reason and one overall winner.
  4. Average the four overall votes for each paper pair, then the pairs within each matchup. A scientist’s score is the mean of its four matchup win rates.

Each opponent contributes 25% of a scientist’s score, regardless of collection size or sampled pair count. Matchup win rates of 40%, 60%, 60% and 80%, for example, give a 60% overall score. The pair cap controls cost.

The published five-system schedule has 96 paper pairs and 384 overall judgments. Nine matchups use ten pairs; v2 versus v3 uses all six possible pairs from their three and two eligible papers. Distinct-paper counts are reported separately from pair and judgment counts. Repeated appearances do not add independent papers.

New plans use the NUS rubric by default, with the AUT-inspired rubric available as an option. Both request one overall preference. See why one overall judgment for the rationale. The published comparison uses its recorded rubric and judgments; selecting another rubric creates a new experiment and does not rejudge saved results.

Run the pipeline

Run these commands from the repository root. Planning and reporting are local; judging makes paid provider calls using credentials already in the environment. The worker and spend overrides below match the expanded comparison.

python3 -m pip install -e '.[ais,test]'
python3 -m crest_ais plan
python3 -m crest_ais judge --workers-per-judge 16 --max-spend-usd 150
python3 -m crest_ais report --report-path crest_ais/results/local-report.html

Planning creates a new experiment. Judging and reporting use the latest planned run unless you pass --run-dir with a specific result directory. Use that option to resume an experiment or inspect a saved run. The report path above writes a separate local report.

Choose the rubric file

The JSON rubric field resolves relative to the configuration file. In a configuration under crest_ais/configs/, select the default NUS rubric with:

"rubric": "../../crest/prompts/nus_pairwise_v2.txt"

To select the optional AUT-inspired rubric, use:

"rubric": "../../crest/prompts/aut_research_pairwise_v1.txt"

The earlier NUS v1 wording is also available as ../../crest/prompts/nus_pairwise_v1.txt. The old AIS paths ../prompts/rubric_v2.txt and ../prompts/rubric_v1.txt remain compatibility aliases for the corresponding NUS files. Both pipelines use the canonical prompts in crest/prompts/ for new configurations.

Create a new plan when changing the rubric. Prepared paper text can be reused, but a changed prompt creates distinct judgment identities. Keep each ranking within its recorded rubric; do not mix NUS and AUT-inspired votes.

What the intervals cover

The ranges describe sensitivity to which eligible paper pairs were sampled, holding the papers, judges, prompts and orders fixed. Small samples produce wide ranges.

The sample size and five-system cohort were chosen after observing earlier results. The ranges therefore serve as exploratory references, without a 95% coverage guarantee. Four-system and five-system scores average different opponents and are not directly comparable.

Paper pairs are the sampling units; a paper can appear in multiple pairs. The calculation holds each possible pair’s judge responses fixed. It excludes variation from repeated calls, model changes, human agreement and future papers. Reusing Sakana Agentic Scientist (v3)’s two papers does not add independent papers.

The calculation combines Serfling sampling-without-replacement bounds, a Bonferroni correction across matchups, and the possible win rates of unsampled pairs. Sampling all pairs removes pair-selection uncertainty, while the other limits remain.

Collection and evidence limits

One v2 run used a manually downloaded and reduced pest-detection dataset. This setup assistance is disclosed; the generated manuscript remains included because the authors report no human edits to its scientific content. See the v2 setup description and manuscript-generation account.

  • Original PDFs, sources, checksums, duplicate records, and access limits are saved under crest_ais/data/.
  • Extracted text has page markers. Identifiable provenance headers are masked, while full text and an audit remain available. Plot images are not visually judged, and extraction can lose equations or reading order. Content can still reveal provenance.
  • Judges read the supplied text without replicating experiments or establishing historical novelty. No human or domain-expert validation of this panel has been performed.
  • Missing judgments become neither losses nor zeroes. Charts come from saved results. Verbatim judge reasons are assessments to check against the linked papers.

Code and verification

Code and run records live in crest_ais/. Runs retain exact inputs, rubric, seed, settings, judgments, usage, and errors. Paper text is data, never an instruction to the judge. Reporting uses the saved prompts, presentations and settings.

Provider adapters preserve remote job IDs, raw responses, and safe resume behavior. Credentials come from the environment.

Tests cover label reversal, unequal-count normalization, incomplete blocks, duplicate/invalid results, finite-pool sampling, content-sensitive caches, safe resume, PDF integrity, path checks, and HTML escaping.
