CREST pipeline

Research pipeline

Generate once, judge complete answers in both orders, and rank the observed preferences with uncertainty.

The experiment

Caesar, OpenAI research, and Gemini Deep Research independently answer the same 50 questions. The dataset is bundled in crest/data/queries_n50.jsonl, copied byte-for-byte from Rome's 50-question file. Loading preserves each exact query string.

150planned answers · 50 × 3 systems
600planned judgments · 3 pairs × 2 judges × 2 orders × 50
1overall A/B winner per judgment, guided by New, Useful, and Surprising

This is an exploratory comparison of the saved answers under the selected judges and rubric. A ranking is not an absolute measurement of creativity or evidence that all future answers will follow the same ordering.

Run the three stages

Use Python 3.11–3.13 and install the project and Rome dependencies as described in Getting started. Export OPENAI_API_KEY and GOOGLE_API_KEY or GEMINI_API_KEY; CREST does not automatically load credentials from dotenv files.

python -m crest plan --config crest.mbp.yaml --limit 1
python stage1_generate.py --config crest.mbp.yaml --limit 1

# Replace the placeholder with stage 1's printed run_dir.
CREST_RUN=results/YYYY-MM-DD/UTC-TIMESTAMP-UNIQUE-ID
python stage2_judge.py "$CREST_RUN" --config crest.mbp.yaml
python stage3_analyze.py "$CREST_RUN" --config crest.mbp.yaml

Planning is local. Generation and judging make paid calls; analysis is local. Omit --limit 1 for all 50 questions. The default configuration is crest.yaml; crest.mbp.yaml selects the measured-resource profile for the 64 GB jason-mbp. Complete the pilot before starting the first full Caesar batch. python -m crest run runs all stages. Later stages otherwise select the latest generation run, so use an explicit result path when managing multiple experiments.

To recover an existing run, repeat stage 1 with --run "$CREST_RUN", then repeat stages 2 and 3. Completed work is reused; remote job IDs are retrieved after interruption. Ambiguous submissions require manual reconciliation before retrying and are never blindly resubmitted.

Budgets and parallelism

$5 per answer is a target, not a guaranteed cap. All 150 answers target $750; judging costs extra. Caesar reserves estimated request costs against a $5 SDK/handler guard and keeps $3 for synthesis, reducing exploration and Q&A when needed. Its per-answer limit is 7,200 seconds and per-call timeout is 600 seconds. New exploration pages stop after 45 minutes; accepted calls finish before ingestion. Q&A reserves 300 seconds per remaining writing/refinement/merge call. These time allocations improve the chance of completion but cannot guarantee a complete answer before the deadline. Native provider APIs expose no hard dollar cap. Gemini research costs use a conservative estimate; an estimated overrun is not a final invoice. Cost reports retain failed paid attempts, partial observations, and unknown bills.

Each provider gains a slot after two successful uncached jobs and halves capacity on HTTP 429. Shared cooldowns honor available retry/reset headers. Native background-job creation retries only explicit 429 rejections; idempotent polling/cancellation also retry transient failures, with four total attempts. Caesar separately allows bounded SDK retries for 429 and server 5xx errors, retaining reservations for uncertain failed attempts against its budget. Limits apply per pipeline process; other account traffic and hosted-agent usage can still cause rate limits.

Results, snapshots, and cache

results/
  .cache/generation/                 shared answer cache
  YYYY-MM-DD/UTC-TIMESTAMP-ID/
    run.json                        questions, jobs, stage registry
    01-generate-UTC-TIMESTAMP/       answers.jsonl and readable answers/
    02-judge-UTC-TIMESTAMP/          judgments and frozen inputs/settings/rubric
    03-analysis-UTC-TIMESTAMP/       ranking.json, ranking.csv, report.md
    .cache/judgments/               this run's judgment cache
    .cache/analysis/                this run's local analysis cache

Every invocation creates a new timestamped stage folder. Stage 1's answers.jsonl is canonical; Markdown answers are reading copies. Stage 3 identifies and reads its precise stage-2 snapshot.

Canonical answer and judgment rows retain model, usage, cost, and a top-level timing object: UTC ISO started_at/completed_at, duration_seconds, source, and definition. Elapsed time includes provider queueing, polling, retries, and interruptions, excluding local scheduling before execution. Cache hits preserve original durations; older checkpoints are backfilled where possible, with unavailable timestamps or duration left null.

Changing the judge or rubric reuses answers. Changing one researcher's generation settings requires a new generation run and invalidates only affected shared-cache work. Existing runs retain generation snapshots. Concurrency/retry changes preserve paid cache entries. Increment a provider's revision only for intentional fresh calls, not to bypass an unresolved submission.

Judging and ranking

Each judge returns exactly {"reason": "…", "winner": "A"} or the same structure with B. New, Useful, and Surprising inform one holistic choice; there are no criterion winners or numeric weights. The rubric prioritizes substance over length, polish, confidence, or citation count.

Rank by overall wins divided by comparisons on common complete questions, balancing opponents, judges, and answer orders. A complete 50-question run gives each system 400 comparisons. Reports retain ties, opponent cycles, per-judge diagnostics, missingness, and paired whole-question bootstrap uncertainty. Read Research evaluation for the denominator, interpretation, and limits.
